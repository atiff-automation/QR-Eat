## Objective

Implement the approved loyalty, visit and promotion contract in QR-Eat (server +
web), behind a default-off flag, then freeze the API for the Counter.

The single rule: **if a promotion applies to the order/bill, the promotion
applies and the visit does not count; the card stays. If no promotion applies,
the visit counts; on the 3rd visit 10% off (cap RM15) applies and the card
resets.** No customer choice, no cashier choice, no recalculation.

**P6C scope note (approved 2026-11-13) — QR phone input.** The customer phone
field in the QR checkout must behave like a phone keypad: `+` (first position
only) and digits, nothing else. Requirements:
- `inputMode="tel"`, `autocomplete="tel"` (WCAG 2.2 "identify input purpose").
- Strip anything that is not `+` or a digit as it is typed **or pasted**, so a
  pasted `+60 12-345 6789` becomes `+60123456789` rather than failing. The field
  never contains a space.
- Remove the current fixed `+60` badge and the digit-stripping mask: the mask is
  why non-Malaysian numbers are silently mangled today.
- Hint text naming the accepted format, and a `PHONE_INVALID` message with a
  concrete example.
- Do **not** reformat the number back at the customer; show what they typed.
- Cap at 16 characters (`+` plus 15 E.164 digits).
**Server stays tolerant.** `normalisePhone()` keeps accepting separators and
rejecting letters, because it also serves the cashier member search, Counter
attach and older clients. The client constrains input; the server validates
meaning. Do not tighten the API to reject spaces — it would break the counter
search.
Research basis: GOV.UK Design System phone-number pattern (allow different
formats, avoid input masking, avoid reformatting) and the keypad-consistency
rule agreed with the product owner. Add a P10 note so the Counter app matches.

**P8 — Reports.** `gross`, `discounts` by source, `net`, `refunds`, rewards
earned/redeemed, promotion redemptions by scope; remove any double subtraction;
Z/P&L discount line and rounding line.

**P8 plan (approved 2026-11-14).** Inspection found four defects, not one.

**Facts**
- `Order.totalAmount` is **post-discount** (subtotal + tax + service − discount).
- The P&L sets `grossSales = Σ totalAmount` and then `netSales = grossSales - discounts - refunds`
  — subtracting a discount that is already inside the gross. That is the contract's "never
  subtract a discount from a net figure", live today.
- Refunds are written as `Payment { amount: -x, status: 'PAID' }`
  (`order-adjustment-service.ts` `createRefundPayment`). The P&L queries `status: 'REFUNDED'`,
  which matches nothing; the loyalty report only reads payments attached to a `PaymentBatch`,
  and refund payments have no batch. Refunds therefore report `0.00`.
- The Z report has no rounding line, so a drawer reconciled to the nearest 5 sen does not
  reconcile on paper.

**Decisions**
- **Q1 = B (superseded by Q4).** P&L: `gross = Σ subtotalAmount`, `discounts = Σ discountAmount`
  shown separately. Gross before discount.
- **Q4 = A (2026-11-14, after the first P8 review).** `net = Σ totalAmount − refunds`, with `tax`
  (`Σ taxAmount`) and `service` (`Σ serviceCharge`) exposed as their own fields. Reason: a refund is
  `-Order.totalAmount` (post-tax, post-service), so `gross − discounts − refunds` double-subtracted
  tax and service and reported `-(tax+service)` for a fully refunded taxed order. The identity is
  `gross − discounts + tax + service − refunds = net`. This matches §18.20.8 `net = Σ totalAmount`
  and makes the P&L agree with the loyalty report and the Z.
- **Q2 = A.** A refund belongs to the business date on which it happened (the money leaving the
  drawer), not the original sale date — a filed day's Z is never silently changed.
- **Q3.** The rounding line goes in the **Z report only**.

**Scope**
1. `src/app/api/admin/reports/profit-loss/route.ts` — gross from `Σ subtotalAmount`; refunds from
   **negative payments** in the range; `net = gross − discounts − refunds` with no double
   subtraction.
2. `src/lib/services/loyalty-report-service.ts` — refunds from negative payments, attributed by
   the refund's own business date, including refunds with no `PaymentBatch`.
3. `src/lib/services/reporting/counter-report-service.ts` — a rounding line per tender, summed
   from `PaymentBatch.roundingAdjustment`, reconciled against `cashPayable`.
4. Confirm the loyalty report's `gross`/`discounts`/`net` match §18.20.8 exactly.
5. Tests: a refunded order reconciles in the P&L, the loyalty report and the Z; the old arithmetic
   is pinned so the change is deliberate.

**Acceptance criteria**
1. P&L: `net = Σ totalAmount − refunds`, with `gross − discounts + tax + service − refunds = net`;
   a discounted order is not double-subtracted and a fully refunded taxed order nets to zero.
2. P&L refunds equal the sum of negative payments in the range, as a positive magnitude.
3. Loyalty report refunds are non-zero after a refund, attributed to the refund's business date.
4. Z shows a rounding total that reconciles `Σ cashPayable` against `Σ cashReceived − Σ changeGiven`.
5. Loyalty report definitions match §18.20.8.
6. Existing report tests still pass; the arithmetic change is asserted explicitly.

**Non-goals**
Changing the loyalty report's date-range semantics, adding rounding to the loyalty report,
touching payment writes, or changing how refunds are recorded (they already write negative
payments correctly).

**Ownership**
`src/app/api/admin/reports/profit-loss/route.ts`, `src/lib/services/loyalty-report-service.ts`,
`src/lib/services/reporting/counter-report-service.ts`, the matching report UI if a figure label

**P9-10a — Edge client-IP resolution (approved 2026-11-14, "fix both").**

The P9-10 probe (`evidence/P9-10-edge-headers.txt`) disproved the P7a assumption. Railway's
edge **prepends** the client to `X-Forwarded-For` and appends an internal hop that changes per
connection; it also sets `X-Real-IP` to the client and overwrites any client-supplied value.
`trustedIp()` takes the **last** entry, so in production the `EDGE_IP` bucket is keyed on a
per-connection internal hop and limits nothing. The `unknown` warning never fires.

**Decisions**
- The client address is `X-Real-IP`, validated; the first `X-Forwarded-For` entry is the
  fallback, both **only when `RAILWAY_ENVIRONMENT` is set**. Off-Railway neither header is
  trusted: they are client-controlled without a proxy.
- A candidate must be a globally routable address. Reject private, loopback, link-local,
  CGNAT (`100.64/10`), unspecified and multicast values; strip `:port` and `[v6]:port`; strip
  an IPv6 zone id; lowercase IPv6.
- The socket peer is used only when it is globally routable, so Railway's CGNAT hop can never
  become a key.
- A once-per-process canary warns when `X-Real-IP` and `X-Forwarded-For[0]` are both present
  and disagree. That is what a future platform change looks like; it must not be silent.
- `/api/health` reports `edgeIp: { source, xffEntries }` — never an address. The runbook check
  reads this instead of the warning.

**Scope**
- New `src/lib/client-ip.ts` holding the resolver, the sentinel, the unknown warning and the
  disagreement canary. `src/lib/loyalty/trusted-ip.ts` is **deleted** and its three importers
  (`qr/orders/quote`, `qr/orders/create` ×2) plus the two test files move to the new module.
  Exported names stay the same, so call sites change only the import path.
- `src/app/api/health/route.ts` takes the request and adds the `edgeIp` block.
- Tests: replace the case that asserts `X-Real-IP` is ignored (it encodes the false
  assumption); add forged-header, multi-entry, port-form, private/CGNAT, non-IP and
  Railway-on/off cases; assert the canary fires once.

**Non-goals**
Changing the rate-limit buckets or limits; changing the audit/security writers (P9-10b);
adding a proxy-mode configuration for self-hosting (no such deployment exists).

**Acceptance**
1. On Railway, `trustedIp` returns the client from `X-Real-IP`; `X-Forwarded-For[0]` is the
   fallback; a forged header cannot change the result.
2. Off-Railway, header values are ignored and the socket peer or `unknown` is used.
3. No private, loopback, CGNAT, unspecified, multicast, port-bearing or non-IP value can
   become a rate-limit subject.
4. The canary logs once per process on disagreement, with no address.
5. `/api/health` reports the source and entry count with no address.
6. Full suite green, type-check and build pass.

**Verification**

## Acceptance criteria

1. QR order create accepts optional phone + loyalty consent in the **same** call;
   no second attach, no claim store, no order token, no pending-member step.
2. `POST /api/qr/orders/quote` returns one server quote with `quoteId`,
   `projectedTotal`, `cashPayable`, `visitState`, `rewardLabel` and the
   authoritative `message`; no spend, `daySubtotal`, `minDailySpend` or
   `amountToMinimum`.
3. Quote evaluates the whole current bill/session; order create validates
   `quoteId` + `expectedTotal`; stale/expired/member-mismatched quote returns
   `QUOTE_CHANGED`; a consumed quote cannot be reused, even with a new
   idempotency key.
4. Promotions work at `ORDER`, `CATEGORY` and `ITEM` scopes with eligible base,
   `minSpend`, cap, best-single, no stacking, and tie-break by highest discount
   then lowest promotion id.
5. A promotion **applies** only when eligible base > 0, conditions are met, and
   discount > 0. Scheduled-but-inapplicable promotions do not block the visit.
6. Partial order with any eligible item ⇒ promotion applies ⇒ visit does not
   count. No eligible items ⇒ visit counts.
7. Promotion applies ⇒ no `LoyaltyVisit`, card unchanged, no reset. No promotion
   ⇒ visit counts; on `visitsRequired` the reward applies and the card resets.
8. One visit per customer per business date, enforced by unique constraints and
   the customer/day lock; a second order the same day creates no second visit.
9. `daySubtotal` aggregates paid, non-cancelled, not fully refunded orders on the
   payment business date, before tax/service/discount; below `minDailySpend` ⇒
   no visit (`BELOW_MINIMUM`).
10. The card snapshots the rule at cycle start; settings changes apply to new
    cycles only; before the first card, current settings decide and the first
    visit snapshots.
11. Bill read returns `billRevision`, `member`, `visitState`,
    `promotionScope`/`promotionItems`, `discountLines[]`, `projectedRewardAmount`,
    `projectedTotal`, `preRewardTotal`, `preRewardCashPayable`, `fullPriceTotal`,
    `totalAmount`, `cashPayable`, and (Counter only) `daySubtotal`,
    `minDailySpend`, `amountToMinimum`.
12. Payment validates `expectedTotal`, `expectedCashPayable`, `expectedBillRevision`
    under the lock and returns `BILL_CHANGED`/`AMOUNT_MISMATCH` **before**
    recording any payment. No partial benefit.
13. Payment writes visit, card mutation, `OrderDiscount`, `Payment` rows,
    `PaymentBatch` and the `PAYMENT` idempotency record in one transaction, in
    the contract order: customer/day lock → bill lock → validate → batch
    businessDate/rounding → visit → card → discount → payments → idempotency.
14. `discountSource`/`LOYALTY_REWARD` rows carry `sourceId = LoyaltyVisit.id` and
    `rewardSnapshot`; exactly one of `promotionSnapshot`/`rewardSnapshot` is
    non-null and matches `source`; one ACTIVE discount per order.
15. Money identities hold: `Σ allocation == reward`, allocation ≤ order subtotal,
    `Order.discountAmount == Σ ACTIVE OrderDiscount.amount`,
    `Σ Order.totalAmount == PaymentBatch.totalAmount == Σ Payment.amount`.
16. Cash: discount before tax/service; tax/service recomputed per order from rate
    snapshots; `cashPayable = round5(projectedTotal)` under `NEAREST_5_SEN`
    (equals total under `NONE`); card/e-wallet exact; `roundingAdjustment`
    recorded and within ±0.02; drawer identity
    `Σ cashPayable == Σ cashReceived − Σ changeGiven`.
17. Consent: notice version/text/hash/privacyUrl are server-derived and
    validated in constant time. Missing/stale consent at QR create ⇒ guest order
    + `loyaltyError` (200), no member/consent/visit. Explicit consent capture
    with stale consent ⇒ `CONSENT_STALE` (422). Counter attach without consent
    stays `GUEST`. Withdrawal effects per §18.20.14 B.
18. Security: phone HMAC + masking (country code + last two), full phone only
    with `members:pii` and audited, cross-tenant 404, deny-by-default permission
    table, durable rate limits per §18.20.15 B, trusted edge IP only, no PII in
    logs/evidence.
19. Offline: offline-created order is full price with no visit/discount; an
    online-priced order paid offline keeps its locked promotion and collects
    `preRewardTotal`/`preRewardCashPayable`; no reward, no visit; an ACTIVE
    discount is never removed; a replayed projected reward is rejected or
    flagged, never silently settled.
20. Reports reconcile: `gross`, `discounts` by source, `net`, `refunds` (negative
    payments as positive magnitude), rewards earned/redeemed, promotion
    redemptions by scope; no discount subtracted from net; no double subtraction.
21. Feature flag `LOYALTY_ENABLED` defaults false and requires
    `LoyaltySettings.enabled`; flag off reproduces pre-feature behaviour exactly.
22. Migration is additive with no backfill; pre-migration rows stay valid; both
    fresh-DB and upgrade paths pass on a throwaway Postgres; rollback = flag off.
23. Deployment-order safety: existing Counter builds that omit the new fields
    keep working (additive only; absent fields default to `0.00`/null).
24. UX: `visitState`/`outcome` precedence honoured (`GUEST` > `PROMOTION` >
    `ALREADY_COUNTED` > `BELOW_MINIMUM` > `COUNTS`; `PROMOTION_APPLIED` >
    `REWARD_APPLIED` > `VISIT_COUNTED` > `ALREADY_COUNTED` > `BELOW_MINIMUM` >
    `GUEST` > `NO_BENEFIT`); copy rendered from snapshots, never hardcoded
    "3rd"/"10%"/"RM20"; accessibility per §18.20.13.
25. Promotion scope membership is stored in join tables
    (`PromotionCategory`, `PromotionItem`, `QuotePromotion`) with composite tenant
    FKs; a category, item or promotion id belonging to another restaurant cannot
    be stored. The API still returns `promotionItems[]` and `promotionIds` as
    arrays.
26. The datamodel and the database agree: `prisma migrate diff` from the live DB
    to `prisma/schema.prisma` is empty, and no `Unsupported` field remains in the
    loyalty models. `npm run db:migrate` must be safe to run.
27. No `text = uuid` comparison is needed anywhere in the eligibility path; scope
    lookups use ordinary foreign keys.

## Constraints

- Server is the system of record. Clients render state and send intents.
- Every mutating request carries an idempotency key; retries are safe.
- All queries tenant-scoped by `restaurantId`; composite FKs; cross-tenant tests.
- Phone numbers are PII: normalise, hash, mask; never log or evidence a full
  number. No secrets in prompts, logs, or run logs.
- `decimal.js` only for money; floor to 2dp; same rounding on quote/order/payment.
- Lock order is always customer/day → bill/order. Never invert it.
- Business rules live in `src/lib`, not route handlers.
- No new dependency without approval. No silent scope expansion.
- Do not claim a test passed unless it was run. Do not run
  `npm test -- --runInBand` and report it as `test:ci`.
- Whole-repo lint is red at baseline (62 errors, 11 warnings); it is not a gate.
  Scoped lint on changed files only, reported honestly.
