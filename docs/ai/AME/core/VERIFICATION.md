# Verification

## Purpose

Verification is an independent check that the integrated result meets the original task and the project’s standards.

It is not a summary review. It is evidence-based.

## Independence

The Verifier must:

- be separate from the Implementer;
- receive the original task and acceptance criteria;
- inspect the actual integrated diff;
- run permitted tests;
- check regressions and neighbouring behaviour;
- report evidence and severity;
- avoid relying on the Implementer’s summary.

The Verifier is read-only during initial verification. It does not fix the code it reviews.

## Core rule

> No completion claim without fresh verification evidence.

If a test was not run, say so. If a command failed, report it. If evidence is insufficient, do not PASS.

## Two-axis review

### Spec axis

Does the change implement the original request?

Check:

- acceptance criteria;
- missing requirements;
- partial requirements;
- behaviour not asked for;
- wrong implementation of a requirement;
- edge cases;
- non-goals.

### Standards axis

Does the change follow the project’s documented standards and quality expectations?

Check:

- coding standards;
- architecture boundaries;
- naming and glossary;
- error handling;
- dependency rules;
- test quality;
- duplication;
- abstraction fit;
- scope creep;
- consistency.

Report the axes separately. Do not let a strong spec result hide a standards failure, or vice versa.

## Consistency checks

- Reused existing components/endpoints/patterns?
- New pattern approved and documented?
- Names consistent with `GLOSSARY.md`?
- Error envelope consistent?
- Dates, money, IDs, enums consistent across layers?
- Duplicated business logic?
- UI states consistent with the state matrix?
- New dependency justified?

## UX/UI checks

For user-facing work:

- main flow works;
- empty, loading, error, success, partial, permission-denied states;
- copy is clear and actionable;
- destructive actions confirm;
- keyboard navigation;
- focus visible and not trapped;
- labels and roles;
- contrast;
- reduced motion;
- responsive breakpoints;
- no layout shift;
- performance budget.

## Frontend checks

- component reuse;
- no one-off design values outside tokens;
- state and data-fetching consistency;
- forms and validation;
- error boundaries;
- API contract respected;
- tests at the right level;
- no duplicated UI logic.

## Backend checks

- API matches contract;
- authorization on every endpoint;
- validation at the boundary;
- money, dates, IDs, enums;
- transaction boundaries;
- idempotency where required;
- migration safety;
- error model;
- observability;
- no secret leakage.

## Security checks

- authentication and authorization;
- input validation and injection;
- IDOR/tenant isolation;
- CSRF/XSS/SSRF;
- session/token handling;
- secrets and key handling;
- sensitive data in logs;
- dependency and supply-chain risk;
- rate limits/abuse controls;
- payment scope.

## Data checks

- schema constraints;
- indexes;
- backfill correctness;
- migration rollback/forward-fix;
- retention/deletion;
- test data anonymization;
- backup/restore implications.

## Reliability checks

- retries and backoff;
- idempotency;
- duplicate processing;
- webhook signatures/replay;
- queue/dead-letter;
- failure visibility;
- reconciliation;
- alerts.

## Test quality

A test is not valuable just because it passes.

Reject:

- tautological tests;
- implementation-coupled tests;
- tests that assert the bug’s wrong behaviour;
- snapshots generated by the implementation itself;
- tests that cannot fail on the bug;
- skipped tests presented as passing.

Prefer:

- behaviour at public seams;
- regression tests that fail before the fix;
- contract tests;
- realistic fixtures;
- deterministic tests.

## Review report

The Verifier returns structured findings, but remains read-only. The Lead writes
them to:

```text
docs/ai/runs/<task-id>/REVIEW-<n>.md
```

Use `templates/REVIEW_REPORT.md`. Record:

- verdict;
- findings by severity;
- evidence;
- not verified;
- residual risk;
- routing.

The Lead updates the `TASK.md` state header. The remediation step consumes the review path, not a
retyped prompt.

## Evidence

Required:

- commands run;
- full output or relevant excerpt;
- exit codes;
- diff or commit range;
- screenshots for UI where relevant;
- test names and results;
- what was not verified.

Redact secrets and PII.

## Verdicts

### PASS

Acceptance criteria met; evidence sufficient; no material findings.

### PASS WITH NOTES

Acceptable, but with recorded residual risk or non-blocking findings.

### FAIL

Acceptance criteria not met, or evidence insufficient, or a material defect/risk exists.

No other verdict is valid.

## Limitations

- Same-model verification can share blind spots.
- “Read-only” is policy, not a sandbox.
- A verifier can miss design flaws if the rubric is weak.
- Automated accessibility tools catch only part of the problem.
- Lab performance is not field performance.
- Contract tests prove compatibility, not product correctness.

For R2/R3, consider a different model, a clean environment, CI, and human review.

## Verifier handoff

The Verifier receives:

```text
TASK.md path and revision:
Risk:
Acceptance criteria:
Diff base and commit:
Files changed:
Test commands:
Specialist findings:
Known limitations:
```

The Verifier returns the report structure. The Lead writes it to
`docs/ai/runs/<task-id>/REVIEW-<n>.md` and updates the `TASK.md` state header.

```text
Verdict:
Spec findings:
Standards findings:
Consistency findings:
UX/UI findings:
Security/data/reliability findings:
Evidence:
Not verified:
Residual risk:
Recommended next action:
```
